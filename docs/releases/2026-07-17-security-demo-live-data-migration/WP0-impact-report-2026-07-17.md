# WP0 Impact Report - V3.3 Security, Demo Access and Live Data Migration

Prepared: 2026-07-17  
Scope: repository reconnaissance, database confirmation, route/action inventory, schema impact map and first implementation boundaries.  
Status: WP0 complete for planning. No Prisma schema changes or data migrations were made.

## Executive Finding

V3.3 is a cross-cutting security and migration release, not a narrow feature release. The current app is a single-user/private app protected by a perimeter PPS access token for remote traffic. It has no named-user authentication, no session-backed authorization context and no server-side workspace/project access enforcement yet.

The correct first implementation path is:

1. Keep live and development databases separated.
2. Build read-only inventory and fingerprint tooling first.
3. Add authentication and authorization services before exposing any demo access.
4. Add `Workspace` and nullable project scope only after the route/action impact is understood.
5. Rehearse every data operation on a copied database before production cutover.

## Current Access and Security Baseline

### Existing perimeter gate

`proxy.ts` protects remote/non-local requests using `PPS_ACCESS_TOKEN`. Localhost requests bypass the token gate unless forwarded headers indicate remote access. The token can be supplied by query parameter, cookie or `x-pps-access-token` header.

This remains useful as a perimeter control during transition, but it is not user identity and not authorization.

### Missing security capabilities

The repository currently lacks:

- Named account authentication.
- Session-backed `requireUser` or equivalent.
- User identity linkage separate from the existing `User` business/profile record.
- Workspace membership.
- Project membership or assigned-project authorization.
- Central authorization context.
- Server-side route/action/export guards.
- Security audit event model.
- Demo viewer read-only enforcement.

## Schema Impact Map

### Current `User` role

`User` currently exists as a business/person record for operational ownership and agent activity, not as an authentication identity. Existing relations must be preserved.

Current `User` relations include:

- `ProjectRisk.ownerId`.
- `ProjectRiskAction.ownerId`.
- `RiskAssessment.assessedByUserId`.
- `RiskReview.reviewedByUserId`.
- Agent instruction, approval, action log and configuration log user fields.

## Data Access Inventory

Data access is currently distributed across:

- App route/page/action files.
- Domain query modules under `lib/domain/**`.
- Shared reporting modules under `lib/reporting/**`.
- Status helpers under `lib/status/**`.
- Operational scripts under `scripts/**`.

V3.3 should not try to patch each query ad hoc. It should introduce a central authorization layer and scoped query helpers, then migrate critical surfaces in priority order.

Recommended new service boundaries:

- `lib/auth/session.ts`: session resolution and `requireUser`.
- `lib/auth/authorization.ts`: `requireAuthorizationContext`, `requireWorkspaceRole`, `requireProjectCapability`.
- `lib/auth/scopes.ts`: helpers for workspace/project filters.
- `lib/audit/auditEvent.ts`: append-only audit writer.
- `scripts/migrations/v3_3_security_preflight.ts`: read-only inventory.
- `scripts/migrations/v3_3_security_backfill.ts`: dry-run/apply backfill after approval.

## Implementation Blast Radius

### Required capability categories

- Owner/admin access to all live and demo workspaces.
- Project manager access only to assigned live projects.
- Demo viewer read-only access only to demo workspace/project data.
- Admin/configuration access restricted to owner/admin.
- Export access restricted to authorized project/workspace data.
- Mutation access denied for demo viewer, including direct server-action invocation.

### Query pattern changes

Current patterns such as `findUnique({ where: { id } })` for project-scoped records must be replaced or wrapped so they also prove authorized scope. Typical target pattern:

```ts
const context = await requireAuthorizationContext();
await requireProjectCapability(context, projectId, "PROJECT_VIEW");

const project = await prisma.project.findFirst({
  where: {
    id: projectId,
    workspaceId: { in: context.workspaceIds },
  },
});
```

### Mutation pattern changes

Server actions must derive authorization from session/context, not from submitted hidden fields. Hidden `projectId`, `workspaceId`, `userId` and role-like inputs must be treated as untrusted selectors.

## WP1 Recommendation

Next deliverable should be WP1, still before schema migration:

1. Create a read-only preflight script that reports:
   - resolved DB path, byte size, SHA-256 and timestamps;
   - SQLite integrity and foreign-key checks;
   - Prisma migration history;
   - table counts;
   - project/user/organization/contact inventory;
   - orphan checks for project/user/status relations;
   - candidate owner `User` records for operator approval.
2. Add a machine-readable report schema under the V3.3 docs folder.
3. Add operator runbook steps for:
   - live backup;
   - sandbox/rehearsal copy;
   - approval of canonical DB fingerprint;
   - rollback evidence.
4. Add guardrails so destructive scripts refuse `PROTECTED_LIVE` unless an explicit production-cutover flag and approved fingerprint are supplied.

## Open Decisions

- Authentication provider/library must be selected only after checking compatibility with Next.js 16.2.4, local Windows hosting, Tailscale Serve HTTPS and future callback requirements.
- Owner `User` record must be explicitly operator-approved. Do not infer ownership from display name alone.
- Whether `Organization` and `OrganizationContact` get direct `workspaceId` in V3.3 or are handled by a transitional rule.
- Whether `ProjectMembership` is required immediately or whether workspace role plus project manager/contact assignment is enough for the first project-manager phase.
- Whether `Session` should be custom or delegated to the selected auth library.

## Non-Negotiable Release Gates

- One codebase continues to support both live and demo.
- No live migration without rehearsal evidence.
- No demo data cloned from live.
- Existing primary keys and relations preserved.
- Status homogenization remains closed; no duplicate status architecture.
- Demo viewer cannot access live IDs through direct URLs, exports or server actions.
- Owner mobile HTTPS workflow remains working after security activation.
- Rollback restore is rehearsed and documented.
